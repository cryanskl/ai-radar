# 04 排名与推荐方法

## 1. 文档目的

AI Radar 会展示“最新”“趋势”“精选”和若干垂直榜单，但不把不同含义的信号混成一个神秘总分。

本文件定义 Public Alpha 的公开方法论，供以下场景共同使用：

- 首页与各内容域的信息流排序。
- 模型评测与性价比榜单。
- GitHub New & Rising。
- 论文、产品、Prompt、Skill 与 Guide 的趋势或精选页面。
- Search 的非文本相关性信号。
- Ask Agent 对“最近最重要”“现在最热门”等问题的解释。
- 公开 API 与开放数据中的排名字段。

这是一份产品规则，不是一组永不变化的权重。具体参数必须版本化、可回放、可解释。

## 2. 核心原则

### 2.1 一个榜单只回答一个问题

| 标签 | 回答的问题 | 不代表什么 |
|---|---|---|
| Latest / 最新 | 最近发生或发布了什么 | 不代表重要或优秀 |
| Trending / 趋势 | 在给定窗口内，什么正在获得异常增长的关注 | 不代表长期质量 |
| Featured / 精选 | 编辑基于公开标准认为哪些内容值得优先阅读 | 不代表客观第一 |
| Benchmark / 评测 | 在指定任务、数据集和条件下，谁表现更好 | 不代表所有场景更强 |
| Value / 性价比 | 在指定质量门槛和成本口径下，谁更经济 | 不代表绝对能力最强 |

页面不得用“Top”“Best”“第一”等文案掩盖榜单条件。

### 2.2 先定义不可比较，再做比较

当对象的任务、版本、价格单位、评测条件或时间窗口不一致时，默认不可直接排名。系统应展示：

- Insufficient evidence / 证据不足。
- Not comparable / 条件不可比。
- Stale data / 数据已过期。
- Methodology changed / 方法已变更。

空缺是有效结果，不应使用估算值填满榜单。

### 2.3 事实、计算与编辑判断分开

每条排序结果都区分：

1. 原始事实：发布时间、价格、评测分、Stars、引用来源等。
2. 派生指标：增长率、标准化分位数、性价比、时间衰减等。
3. 编辑判断：Featured 原因、主题相关性、重要性说明。

数据库和 API 中不得用同一个字段混放三类信息。

### 2.4 排名可追溯

用户至少能看到：

- 榜单名称与用途。
- 统计窗口和数据截止时间。
- 样本量与覆盖范围。
- 指标单位。
- 数据来源。
- 方法版本。
- 已知限制。
- 对异常或更正的说明。

## 3. 通用排名对象

### 3.1 Ranking Definition

每个榜单由一个公开定义描述：

| 字段 | 含义 |
|---|---|
| ranking_id | 稳定的榜单标识 |
| title_en / title_zh | 双语榜单名称 |
| question | 榜单回答的具体问题 |
| entity_type | 被排名的对象类型 |
| eligibility | 进入榜单的最低条件 |
| window | 统计时间窗口 |
| dimensions | 使用的指标维度 |
| normalization | 跨来源或跨指标标准化方法 |
| tie_breaker | 同分时的公开规则 |
| version | 方法版本 |
| effective_at | 当前版本生效时间 |
| limitations | 已知限制 |

### 3.2 Ranking Observation

榜单中的一行不是实体的永久属性，而是一次带时间的观察：

| 字段 | 含义 |
|---|---|
| ranking_id | 所属榜单 |
| entity_id | 被观察实体 |
| observed_at | 观察时间 |
| rank | 当前名次，可为空 |
| score | 当前计算值，可为空 |
| raw_metrics | 参与计算的原始指标 |
| confidence | high、medium 或 low |
| evidence_refs | 支撑数据的来源 |
| methodology_version | 计算方法版本 |
| status | active、insufficient、stale、withdrawn |

历史观察保留，因此用户可以查看趋势，而不是只看到随时会变化的当前数字。

## 4. Latest / 最新

### 4.1 排序规则

Latest 是最简单、最可预期的排序：

1. 事件使用 first_published_at 或 event_occurred_at，不能用本站抓取时间冒充发布时间。
2. 实体发布使用 release_at 或 published_at。
3. 时间相同时，以更高来源确定性优先；再次相同时使用稳定 ID，确保分页不跳动。
4. 内容更新不会无条件顶回最新列表；只有发生了新的独立事件，才生成新的 Event。

### 4.2 时间语义

页面明确区分：

- Occurred / 事件发生时间。
- Published / 来源发布时间。
- Discovered / AI Radar 首次发现时间。
- Updated / AI Radar 记录更新时间。

如果只有日期没有精确时刻，系统不得伪造分钟级时间。

## 5. Trending / 趋势

### 5.1 趋势的定义

Trending 衡量“在一个限定时间窗口内，相比其正常基线正在异常增长的注意力”，而不是简单累加总量。

Public Alpha 可使用以下组件：

- Velocity：观察值增长速度。
- Source-normalized percentile：在同一来源、同一时间窗中的分位数。
- Cross-source breadth：是否有多个独立来源出现一致信号。
- Freshness decay：随时间衰减。
- Confidence：数据完整度和来源稳定性。
- Integrity adjustment：已确认的刷量、重复或异常流量修正。

概念形式：

~~~text
Trending score
= normalized velocity
+ cross-source breadth
+ freshness contribution
x confidence
- confirmed integrity penalties
~~~

具体权重不在产品文档中写成永久常量。它们由方法版本管理，并在 Trust Center 公布当前值与变更记录。

### 5.2 为什么必须按来源标准化

不同平台的数字不可直接相加：GitHub Stars、Hacker News 讨论、论文下载、官方公告引用和中文社区转发不在同一量纲。系统先在各自来源与窗口内计算位置，再合并信号。

这样可以避免：

- 大平台天然压过小而专业的来源。
- 英文来源因总体流量更大而长期占满全球榜。
- 绝对累计量让旧项目永远占优。
- 一次性爆发被误解为长期质量。

### 5.3 全球与语言视图

AI Radar 提供：

- Global：跨语言合并后的全球趋势。
- English signals：主要由英文来源形成的趋势。
- Chinese signals：主要由中文来源形成的趋势。

语言视图是信号来源的过滤，不是事件事实的重复副本。同一 Event 仍只有一个稳定身份，并拥有中英文呈现。

全球榜必须披露来源覆盖不均衡。不得把“未覆盖某地区”写成“该地区没有动态”。

### 5.4 默认窗口

Public Alpha 建议提供：

- Now：滚动 24 小时。
- Week：滚动 7 天。
- Month：滚动 30 天。

每种指标可根据来源更新频率使用更合理的采样粒度，但页面必须显示实际窗口。

## 6. Featured / 精选

Featured 是编辑选择，不伪装成算法结果。

每条精选记录包含：

- 选择人或编辑角色。
- 选择时间。
- 双语推荐理由。
- 适用人群。
- 关联主题。
- 商业关系披露。
- 过期或撤下状态。

可选标准：

- 对行业方向有显著影响。
- 提供高质量一手材料。
- 能帮助用户理解复杂变化。
- 在主流热度之外具有独特价值。
- 对中文或英文读者存在明显信息差。

付费合作、赞助和联盟关系不得改变 Featured 或自然榜单排名。商业内容使用独立视觉和字段标识。

## 7. 模型榜单

### 7.1 不做万能总榜

模型能力受任务、提示策略、工具权限、上下文长度、采样参数、硬件、评测版本和发布日期影响。Public Alpha 不发布一个覆盖所有用途的“万能总分”。

模型页按场景组织，例如：

- Coding。
- Reasoning。
- Long context。
- Multimodal understanding。
- Image generation。
- Video generation。
- Open-weight deployment。
- Low-latency serving。
- Agent/tool use。

### 7.2 评测记录最低字段

| 字段 | 要求 |
|---|---|
| model_version | 精确到可识别版本，不能只写品牌名 |
| benchmark_version | 数据集与评测版本 |
| task | 评测任务 |
| score / unit | 原始分数和单位 |
| higher_is_better | 明确方向 |
| run_date | 运行或发布日期 |
| evaluator | 官方、第三方或 AI Radar |
| settings | 能获得的关键参数 |
| evidence_url | 原始报告或结果页 |
| reproducibility | 是否可复现 |
| confidence | 可信等级 |

缺少模型版本、评测版本或原始来源时，不进入可比较主榜。

### 7.3 榜单来源分层

- Independent reproduced：独立且可复现，优先级最高。
- Independent reported：独立第三方报告，但不完全可复现。
- Vendor reported：厂商自报，保留并明确标记。
- Community observation：社区观察，只用于补充，不进入高置信主榜。

来源分层不是简单给厂商分数打折；更诚实的做法是并列展示来源与置信度。

### 7.4 性价比

性价比必须先选择质量门槛和使用场景，再计算成本。

允许的表达：

- 在 Coding 评测达到某门槛的模型中，每百万输出 token 价格最低。
- 在指定图像质量档位中，每张标准尺寸图片成本更低。
- 在同一硬件和吞吐设置下，开放权重模型的单位请求推理成本。

不允许的表达：

- 将输入 token、输出 token、缓存、批处理和订阅套餐混成一个价格。
- 用一次促销价代表长期价格。
- 用厂商 API 价直接对比未包含硬件、人力和利用率的自部署价。
- 在评测条件不同的模型之间计算虚假的“分数除以价格”。

每个 Value 榜单展示：

- 价格地区与币种。
- 价格生效时间。
- 输入、输出、缓存或媒体单位。
- 质量门槛。
- 汇率与税费是否计入。
- 自部署成本假设。
- 数据更新时间。

### 7.5 模型配置推荐

配置推荐不是排行榜的另一种名字。它根据任务约束生成候选集：

- 任务类型。
- 质量优先级。
- 时延要求。
- 预算。
- 数据与部署约束。
- 地区可用性。
- 是否需要开放权重。

结果展示“为什么适合”和“在哪些情况下不适合”，并引用对应模型档案、价格记录和评测证据。

## 8. GitHub New & Rising

### 8.1 目的

GitHub 榜回答“哪些 AI 开源项目近期正在获得真实关注或持续维护”，不等同于“代码质量最好”。

### 8.2 候选指标

- 新增 Stars 的速度与同龄仓库分位数。
- Forks 与贡献者增长。
- Release 新鲜度和发布节奏。
- Issue 与 Pull Request 活跃度。
- 最近提交活跃度。
- 跨来源提及。
- 仓库年龄。
- License 是否明确。

累计 Stars 只作为背景信息，不能主导 Rising。

### 8.3 资格与异常

- 仓库必须与 AI 主题有明确关系。
- Fork、镜像和模板生成仓库需要识别，避免重复。
- 缺少 License 的仓库仍可被发现和链接，但不能被标记为可自由复用。
- 已归档、删除、转私有或被安全警告的仓库需要更新状态。
- 已确认的异常增星从趋势计算中修正，并留下说明。

## 9. 论文趋势

论文的 Trending 只代表近期关注，不代表学术质量或结论正确。

Public Alpha 可结合：

- 首次发布和修订的新鲜度。
- 同领域、同窗口内的下载或浏览信号，在来源允许时。
- 代码实现、模型发布和产品采用等跨实体关系。
- 多个独立专业来源的讨论。
- 编辑选择。

引用量是慢变量，且数据库覆盖不一，不适合直接决定新论文趋势。若以后引入引用指标，必须注明来源、学科差异和更新时间。

论文详情始终优先展示摘要、作者、版本、原始链接、代码与关联实体，而非突出一个不透明热度分。

## 10. 产品趋势

产品趋势可观察：

- 正式发布与重大版本更新。
- 公开用户或采用信号，且来源可核验。
- 独立来源覆盖广度。
- 与模型、企业或生态事件的关系。
- 价格与可用地区变化。

下载量、收入、用户数等厂商自报数据必须标记为 Self-reported。若没有可比数据，产品页采用趋势、精选和分类浏览，不制造“全球 AI 产品总榜”。

## 11. Prompt、Skill 与 Guide

Public Alpha 不给 Prompt、Skill 和 Guide 做跨任务的“最好”总榜，因为它们的有效性高度依赖模型、版本、输入和预期输出。

允许的排序：

- Latest：最近发布或验证更新。
- Trending：收藏、复制、运行反馈或跨来源关注的时间窗口趋势；只有存在可靠数据时启用。
- Featured：编辑挑选并说明理由。
- Task fit：按任务、模型、工具和输入类型筛选。

内容卡必须显示：

- 适用模型或工具及版本。
- 作者与来源。
- 授权状态。
- 最后验证时间。
- 输入与预期输出示例。
- 已知限制或安全提示。

用户提交不能仅凭提交量进入推荐位。

## 12. Search 与 Ask 中的推荐

### 12.1 Search

Search 的第一目标是相关性，不是热度。基础排序依次考虑：

- 查询与标题、别名、摘要、实体字段的文本相关性。
- 中英文跨语言匹配。
- 实体与事件类型匹配。
- 时间过滤。
- 用户明确选择的排序方式。

趋势只作为弱信号或显式排序选项，不能让热门内容吞掉更准确的结果。

### 12.2 Ask

Ask 回答“最热门”“最值得关注”时必须：

1. 说明所用榜单或判断标准。
2. 展示统计窗口和数据截止时间。
3. 引用站内证据与原始来源。
4. 区分算法趋势与编辑精选。
5. 在证据不足时明确拒绝给出确定名次。

## 13. 冷启动

Public Alpha 初期数据稀疏，按以下顺序处理：

1. Latest 使用确定时间，不需要冷启动猜测。
2. Trending 只有达到最低观察数和来源数时才展示名次。
3. 不足时退化为“Rising signals / 上升信号”，不显示精确名次。
4. Featured 由编辑补足高价值发现，但明确标记。
5. 榜单页面展示覆盖率和缺失项。

禁止通过手工填写算法分数伪装成自动趋势。

## 14. 反操纵

只处理在系统边界真实存在的风险，不为假设场景堆积规则。Public Alpha 的最低措施：

- 同一来源的重复内容在 Event 聚类后只贡献一次主要信号。
- 平台计数先做来源内标准化。
- 已确认的机器人或异常流量从计算中排除。
- 用户提交、赞助关系和站内点击不得直接提升自然排名。
- 编辑 Featured 与算法 Trending 使用独立字段和 UI。
- 每次人工修正保留原因和审计记录。

## 15. 方法版本与变更

方法变更分三类：

| 类型 | 示例 | 处理 |
|---|---|---|
| Patch | 修正解析或明显计算错误 | 保留版本记录并重算受影响窗口 |
| Minor | 增加新来源或新信号 | 发布变更说明，允许新旧结果短期并存 |
| Major | 改变榜单问题、归一化或核心指标 | 新方法版本，不覆盖旧历史 |

历史 API 记录携带 methodology_version。页面显示最近一次重大变化，并链接到完整日志。

## 16. 更正与申诉

实体作者、厂商、研究者和用户可以提交：

- 原始数据错误。
- 版本识别错误。
- 重复实体或事件。
- 价格过期。
- 评测条件不可比。
- 归属、授权或商业关系遗漏。
- 可验证的异常流量证据。

更正流程：接收、证据核验、决定、重算、发布说明。不得只修改当前页面而不更新 API、数据快照和历史观察。

## 17. Public Alpha 验收标准

- Latest、Trending、Featured 在页面与数据中是三个独立概念。
- 每个公开榜单都有问题、窗口、来源、方法版本和限制。
- 模型榜至少按场景拆分，不存在默认万能总榜。
- 模型性价比明确成本单位、质量门槛和生效时间。
- GitHub Rising 不由累计 Stars 单独决定。
- 论文趋势明确声明不代表学术质量。
- Prompt、Skill 和 Guide 不使用无证据的“最好”总榜。
- 数据不足时可以不排名，并在 UI 中显示原因。
- Featured 有双语理由和商业关系披露。
- 任何自然排名不接受付费购买。
- 排名记录能追溯到原始指标、证据和方法版本。
- 更正能够传播到页面、API 与后续开放数据版本。
