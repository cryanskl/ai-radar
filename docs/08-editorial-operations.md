# 08 编辑与运营手册

## 1. 目的

AI Radar 的 Public Alpha 由一名 Owner 加 AI 工具运营。本手册把“网站内容很多”转化为可持续的日常流程，避免上线后依赖临时判断。

它覆盖：

- 来源接入与每日采集。
- 事件去重、事实核验和发布。
- 双语本地化。
- Featured 与 Daily Brief。
- 八个内容域的维护节奏。
- 历史回填。
- 更正、撤回、权利和安全事件。
- 数据 Release。
- 质量抽检和运营指标。

## 2. 角色与责任

### 2.1 Owner

Alpha 只有一个最终责任人，负责：

- 来源是否接入。
- 高影响 Event 是否发布。
- 实体合并、拆分和关系审核。
- Featured 选择和推荐理由。
- Daily Brief 最终发布。
- 模型评测与价格可比性。
- Prompt、Skill、Guide 的授权范围。
- 更正、下架与商业披露。
- 数据 Release 签发。

Owner 可以使用 AI 生成候选、摘要和翻译，但不能把责任转交给模型。

### 2.2 自动化

自动化适合：

- 轮询和获取来源。
- 格式标准化。
- 去重候选召回。
- 实体候选链接。
- 语言检测。
- 翻译与摘要草稿。
- 一致性检查。
- 索引、RSS、邮件和数据包生成。
- 新鲜度与失败监控。

自动化不得独立决定：

- 高影响事实的最终真实性。
- 争议事件立场。
- 许可不清内容可否全文发布。
- 模型跨评测的可比性。
- Featured 的编辑判断。
- 下架争议的最终处理。

## 3. 编辑原则

1. 原始来源优先于转述。
2. 事实、观点和推断分开。
3. 一个现实事件只建立一个主 Event。
4. 英文与中文共享事实，但允许不同语言的解释重点。
5. “没有足够证据”优于填满页面。
6. Trending、Featured 和 Sponsored 永不混用。
7. 对外发布前先确认权利状态。
8. 更正公开、可追溯，不静默抹除。
9. 抓取数量不是质量指标。
10. 每条内容都应帮助用户理解、连接或行动，不能只为 SEO 占位。

## 4. 每日运营节奏

以下是建议节奏，不要求固定时区值。全球站需要根据读者分布和来源高峰逐步调整。

### 4.1 每日循环

| 阶段 | 目标 | 主要动作 |
|---|---|---|
| Intake | 确认系统正常接收全球信号 | 查看核心来源新鲜度、采集失败和队列积压 |
| Triage | 找出最值得处理的候选 | 按影响、时效、证据、用户相关性分层 |
| Verify | 建立可信事实 | 找原始来源、核对版本、时间、数字和许可 |
| Structure | 让内容进入知识系统 | 合并 Event、链接实体、添加关系和 Topic |
| Localize | 形成中英文可读版本 | 生成草稿、核对术语与事实、发布或标记待审 |
| Curate | 提供注意力导航 | 更新 Top Stories、Featured 和关键榜单说明 |
| Brief | 压缩当日变化 | 发布中英文 Daily Brief |
| Health | 关闭当天风险 | 检查失败、过期数据、邮件和更正队列 |

### 4.2 时间预算

一人运营时使用影响分层，不承诺审阅所有自动发现内容：

- 40%：核心 Event 与来源核验。
- 20%：实体、关系和排名数据质量。
- 15%：双语 Daily Brief 与 Featured。
- 10%：历史回填。
- 10%：产品与采集健康。
- 5%：社区提交、权利和更正。

比例随事件密度变化；重大事件日暂停低优先级历史回填。

## 5. 候选分级

### 5.1 影响等级

| 等级 | 定义 | 示例处理 |
|---|---|---|
| P0 breaking | 对大量用户有即时影响或存在重大安全、下线、政策变化 | 立即核验；优先双语发布；持续更新 |
| P1 major | 重要模型、论文、产品、价格、开源发布或行业事件 | 当日核验并结构化 |
| P2 useful | 对特定用户群有明确价值 | 按域队列处理 |
| P3 signal | 尚未充分证实或价值有限的早期线索 | 保存候选，不公开或只做低置信信号 |

影响等级不是排名分，也不直接决定 Trending。

### 5.2 处理优先级

优先级由以下问题共同决定：

- 是否影响用户当前决策？
- 是否有一手来源？
- 是否具有跨域关系价值？
- 是否存在明显中英文信息差？
- 是否容易过期？
- 是否有错误传播风险？
- 是否具备公开权利边界？

## 6. Source Intake

### 6.1 新来源申请

来源可以来自：

- Owner 主动发现。
- 系统从外链频率中提示。
- 社区提交。
- 官方机构或作者提交。

每个来源完成以下检查后才能自动采集：

1. 确认发布主体和官方入口。
2. 记录来源等级和覆盖主题。
3. 阅读服务条款、API 规则、robots 和许可。
4. 定义获取方式、频率和速率。
5. 定义允许存储、展示和导出的字段。
6. 运行有限样本测试。
7. 检查是否产生重复、错误时间或乱码。
8. 设置 Owner 与最近复核时间。

### 6.2 来源停用

在以下情况暂停或停用：

- 条款变化导致当前用法不再明确。
- 长期返回错误或结构变化。
- 内容质量明显下降。
- 出现大量无法去重的自动生成内容。
- 权利人提出有效异议。
- 来源被冒充、劫持或出现安全风险。

停用来源不自动删除既有 Event；逐条按证据与权利状态复核。

## 7. Event 编辑流程

### 7.1 候选检查

Owner 打开候选时依次检查：

1. 这是独立事件，还是已有 Event 的另一个来源？
2. 是否能找到 S 级原始来源？
3. 事件主体、动作、对象和时间分别是什么？
4. 标题是否把计划、传闻、测试、预览和正式发布混淆？
5. 数字、价格、版本和地区是否有明确条件？
6. 应连接哪些实体？
7. 来源内容允许保存和展示到什么程度？
8. 是否需要人工双语审核？

### 7.2 标题规范

标题优先采用“主体 + 已核验动作 + 关键对象”，避免：

- 夸张形容词。
- 未经证实的因果。
- 把媒体预测写成已经发生。
- 省略影响判断所需的版本或地区。
- 用“震撼”“王炸”“彻底改变”等流量词。

英文和中文标题不要求逐字翻译，但事实范围必须相同。

### 7.3 摘要结构

Event 摘要建议包含：

- What happened：发生了什么。
- Why it matters：为何值得关注，明确这是编辑解释。
- Key constraints：版本、地区、价格、可用性或限制。
- Evidence：原始来源与独立来源。

短摘要只保留 What happened 和最重要限制；详情页再展开。

### 7.4 来源选择

- 主来源优先官方或作者原始发布。
- 独立媒体用于验证影响和补充背景。
- 社区用于发现反应，不替代事实来源。
- 多家媒体复制同一稿件时只算一个独立信号。
- 来源之间冲突时并列展示差异，不用多数票制造真相。

### 7.5 发布状态

| 状态 | 含义 |
|---|---|
| candidate | 自动或人工发现，未核验 |
| verifying | 正在找证据或解决冲突 |
| ready | 事实、权利和最小本地化已满足 |
| published | 对外可见 |
| updating | 新信息进入，旧版本仍带状态可见 |
| corrected | 已发布更正 |
| merged | 已合并到另一 Event |
| withdrawn | 已撤回或因权利下架 |

## 8. 实体与关系编辑

### 8.1 新实体

创建前搜索：

- 精确名称。
- 别名和旧名称。
- 官方 URL。
- 论文、仓库或模型外部标识符。
- 中文与英文译名。

如果不确定是家族还是版本，宁可建立待审候选，也不直接合并。

### 8.2 关系审核

每条公开 Relation 必须回答：

- 主体是什么？
- 动作是什么？
- 对象是什么？
- 关系何时有效？
- 哪个来源证明？
- 是事实、声明还是 AI Radar 推断？
- 置信度和审核状态是什么？

例如，Repo 声称实现 Paper 时可标为 IMPLEMENTS；仅在 README 中提到论文不一定代表完整实现，需要按证据调整置信度。

### 8.3 Backlink 质量

每周抽查高连接实体：

- 是否因别名错误出现无关链接。
- 同一模型不同版本是否被混淆。
- 组织与产品关系是否过期。
- Event 时间线是否有重复或倒序。
- 关系证据链接是否仍可访问。

## 9. 双语编辑流程

### 9.1 三层内容

| 层 | 处理方式 |
|---|---|
| 系统 UI 与政策 | 人工编写和审核，必须完整双语 |
| 高影响 Event、Featured、Brief | AI 草稿 + Owner 审核 |
| 普通实体与低影响 Event | AI 草稿 + 结构化一致性检查；状态显式展示 |

### 9.2 术语规则

- 模型、产品、仓库和公司官方名称保留原文。
- 首次出现的关键术语可使用“中文（English）”。
- 不强行翻译 API、Token、Benchmark、Agent、Prompt、Skill 等已经被目标读者广泛使用的术语；词表保持一致。
- 同一模型版本在全站只使用一个规范显示名。
- 译名存在争议时保留原名并记录别名，不擅自统一行业用法。

### 9.3 一致性检查

发布前比较中英文：

- 数字、价格和单位。
- 日期与时区。
- 模型和产品版本。
- 否定词、范围和可用地区。
- 引用数量与来源。
- 事实状态，如 announced、preview、available、deprecated。

语言风格可以不同，事实不能漂移。

## 10. Featured 运营

### 10.1 选择标准

- 对行业或用户工作有明显影响。
- 提供一手、高质量或可复现材料。
- 能解释多个实体之间的变化。
- 修正了热门叙事中的重要误解。
- 为中英文读者弥补信息差。
- 虽不热门但有长期参考价值。

### 10.2 必填字段

- 选择理由。
- 适用人群。
- 选择时间。
- 编辑角色。
- 相关 Topic。
- 商业或个人利益关系。
- 预计复核时间。

### 10.3 撤下

Featured 可因过期、事实更正、证据撤回或更合适内容出现而撤下。撤下不删除原对象，只结束精选状态。

## 11. Daily Brief

### 11.1 目标

Daily Brief 帮助读者在五分钟内理解当天最重要的全球 AI 变化，不是自动拼接所有最新标题。

### 11.2 建议结构

1. One-line overview / 一句话总览。
2. 3–7 个 Key developments。
3. Models & Research。
4. Products & Open Source。
5. Prompts, Skills & Guides 中真正值得行动的内容。
6. What to watch / 接下来关注。
7. 数据截止时间、覆盖与更正入口。

数量是建议，不是硬凑目标。信息不足时宁可更短。

### 11.3 生成流程

1. 从已发布 P0/P1 Event 和 Featured 建立候选池。
2. 去除同一事件重复表达。
3. 检查八域覆盖，但不为均衡强塞低价值内容。
4. AI 生成英文和中文结构草稿。
5. Owner 核对事实、来源、排序和语气。
6. 预览网页、RSS 和邮件。
7. 冻结版本并发布。
8. 新事实出现时发布更正或更新版本，不悄悄改写已发送邮件。

### 11.4 中英文差异

两版共享关键事实选择，但可以：

- 给中文读者补充海外产品语境。
- 给英文读者补充中国市场和中文社区语境。
- 调整术语解释深度。

不能因为语言不同而改变事实结论或遗漏重大冲突来源。

## 12. 八个内容域的运营节奏

### 12.1 Radar

- 每日持续处理 P0/P1。
- 监控重复 Event 和失效来源。
- 每日复核 Top Stories。

### 12.2 Models

- 新模型与版本当日建档。
- 价格按事件更新，并定期复核关键模型。
- 评测只在条件完整后进入可比榜。
- 弃用、地区和访问变化写成 Event。

### 12.3 Papers

- 自动获取新论文候选。
- 按 Topic、跨域关系和信号筛选，不追求收录全部论文。
- 重点论文补充独立中英文导读、限制和代码关系。
- 修订版与初版关系保留。

### 12.4 Products

- 自动发现更新，人工维护核心档案。
- 价格、可用地区、产品状态和底层模型变化优先。
- 厂商自报数字明确标记。

### 12.5 GitHub

- 官方 API 更新元数据和 Release。
- 每日生成 New & Rising 候选。
- 定期检查 License、归档和维护状态。
- 重点项目补论文、模型、产品和 Skill 关系。

### 12.6 Prompts

- 以原创、投稿、开放许可和授权内容为主。
- 验证适用模型版本与基本输出。
- 模型更新后将旧验证标为 stale。
- 不从社交平台批量复制正文。

### 12.7 Skills

- 检查平台、版本、权限、依赖、License 和维护状态。
- 不运行来历不明的安装命令处理采集。
- 安全状态只陈述实际检查范围。
- 将 Skill 与官方 Repo、Guide 和兼容工具连接。

### 12.8 Guides

- 围绕高频用户任务、重要变化和数据解释编写。
- 设置、价格和 UI 步骤带最后验证时间。
- 过期 Guide 标记 stale 或更新，不让旧教程继续作为默认推荐。

## 13. 模型评测与价格运营

### 13.1 评测录入

逐项核对：

- 精确模型版本。
- Benchmark 和版本。
- 任务与评分方向。
- 运行设置。
- 报告主体。
- 运行或发布日期。
- 原始证据。
- 可复现程度。

厂商自报和独立评测分开标记，不人为改分制造“公平”。

### 13.2 价格录入

- 价格来源必须是官方定价页或明确公告。
- 保存币种、地区、税费口径、单位和生效期。
- 输入、输出、缓存、批处理和媒体价格分开。
- 促销价记录结束时间。
- 自部署估算记录硬件、利用率和不包含项。

价格页到期或来源改变后，旧记录结束 valid_to，不覆盖历史。

### 13.3 推荐审核

模型配置推荐抽检：

- 是否使用过期价格。
- 是否混用不可比评测。
- 是否忽略地区或数据要求。
- 是否解释不适用场景。
- 是否在证据不足时仍给确定第一。

## 14. Prompt 与 Skill 投稿

提交者需要提供：

- 标题与用途。
- 作者身份或公开署名。
- 原始来源。
- 适用模型、工具和版本。
- 许可选择与权利声明。
- 必要的输入输出示例。
- Skill 的依赖、权限和外部 API 要求。

审核结果：accepted、needs_changes、link_only、rejected、withdrawn。

拒绝常见原因：

- 无权提交他人全文。
- 只有营销描述，没有可验证用途。
- 包含密钥、恶意命令或隐藏外联。
- 适用版本不明确。
- 与现有记录重复且没有新增价值。

## 15. 历史回填

### 15.1 范围

主时间线从 2022-11-30 开始，目标 1,000–3,000 个关键 Event。数量不是硬 KPI，覆盖关键转折更重要。

### 15.2 主题批次

按专题回填比逐日抓新闻更有效：

- ChatGPT 与通用对话模型演进。
- 开放权重模型生态。
- Coding Agent 与开发工具。
- 图像、音频和视频生成。
- 长上下文、推理和工具使用。
- 关键论文到模型和产品落地。
- AI 产品与商业模式变化。
- 开源框架、Repo 和 Skill 生态。
- 评测、价格、监管和安全节点。
- 中国与全球生态交叉事件。

### 15.3 每批验收

- 有时间边界和完成定义。
- 每个 Event 至少有一个原始或高质量来源。
- 重复来源已聚类。
- 关键实体和关系已建立。
- 核心内容双语。
- 权利状态完整。
- 随机抽查无明显时间、版本或标题错误。

2022-11-30 前内容进入 Curated Prehistory，不假装覆盖完整。

## 16. Search 与 Ask 质量运营

### 16.1 Search 日志审查

仅收集必要、去标识化的产品信号。每周检查：

- 高频零结果查询。
- 中英文别名缺失。
- 错误实体类型排名靠前。
- 旧版本覆盖新版本。
- 用户重复改写的查询。

修复优先从别名、实体和内容质量入手，不立刻增加复杂模型。

### 16.2 Ask 抽检

样本至少覆盖：

- 最新事件总结。
- 模型比较。
- 时间线。
- 论文到代码关系。
- Prompt 或 Skill 发现。
- 明确超出数据范围的问题。

检查：

- 引用是否支持结论。
- 是否混淆数据截止时间。
- 是否把 Trending 说成 Best。
- 是否忽略证据冲突。
- 是否在应拒答时编造。
- 中文和英文回答是否保持事实一致。

失败案例回到数据、检索或回答规则的具体层修复，不能只修改提示词掩盖脏数据。

## 17. 更正流程

### 17.1 入口

- 每个详情页的 Report / Suggest correction。
- Trust Center 联系入口。
- 作者、组织或权利人的直接请求。
- Owner 主动发现。

### 17.2 处理

1. 记录案例与收到时间。
2. 保存原始主张和证据。
3. 判断事实、翻译、归属、权利、重复或排名问题。
4. 必要时临时标记 reviewing。
5. 核验原始来源并作决定。
6. 更新核心记录。
7. 生成 Correction 或 Tombstone。
8. 刷新页面、Search、API 和后续 Release。
9. 通知提交者，适用时公开说明。

### 17.3 优先级

| 严重度 | 示例 | 目标处理 |
|---|---|---|
| Critical | 敏感个人信息、明确侵权、安全恶意内容 | 立即限制公开并核验 |
| High | 重大事实、错误价格、错误模型版本、错误归属 | 优先于日常编辑 |
| Normal | 翻译、别名、关系或描述问题 | 进入日常队列 |
| Low | 风格、非关键排版或建议 | 按批次处理 |

不对外承诺尚无法保障的固定 SLA，但公开状态和处理结果。

## 18. 下架与权利请求

- 权利请求与普通内容反馈分开记录。
- 验证请求人身份和具体对象。
- 涉及明确风险时先隐藏正文或媒体，保留最小记录。
- 判断 AI Radar 自有表达、事实元数据、第三方引文和原始文件的不同边界。
- 需要下架时使用 withdrawn 和 Tombstone，不复用 ID。
- 下一数据 Release 携带删除或更正指令。
- 争议处理记录不进入公开数据，公开说明只包含必要信息。

## 19. 商业关系与利益冲突

所有以下关系需要披露：

- 赞助。
- 联盟链接或分成。
- 厂商免费额度或设备。
- Owner 的投资、雇佣或顾问关系。
- 受委托内容。

商业内容：

- 不进入自然 Trending 计算。
- 不能购买 Featured。
- 使用独立字段与视觉标识。
- 事实审核标准与普通内容相同。

## 20. 数据 Release 运营

### 20.1 发布前

- 冻结 data_version。
- 运行 rights、privacy 和 schema 校验。
- 检查 Corrections 与 Tombstones。
- 抽检各内容域。
- 生成记录数、许可分布和来源分布报告。
- 验证 checksum。
- 审阅 release notes 和已知限制。

### 20.2 发布后

- 在 GitHub Release 验证下载。
- 将原文件同步到飞书或百度网盘。
- 从镜像重新下载抽查 checksum。
- 更新网站 Open Data 页面。
- 保留 manifest 和发布时间。
- 监控用户报告。

如果镜像失败，规范 GitHub Release 可以保持上线，但国内镜像显示 pending，不能提供旧文件冒充新版本。

## 21. 健康检查

### 21.1 每日

- 核心来源是否过期。
- 采集和解析失败是否集中出现。
- P0/P1 待审是否积压。
- 中英文 Daily Brief 是否发布。
- RSS 和 Email 是否生成。
- Search 索引截止时间。
- Ask 引用失败率。

### 21.2 每周

- 八域新鲜度和真实数据覆盖。
- 来源等级与语言分布。
- 事件重复率抽样。
- 关系证据抽样。
- 模型价格与关键榜单更新。
- stale 本地化和 Guide。
- 零结果 Search 与 Ask 失败样本。
- Corrections 和权利队列。
- 数据备份状态。

### 21.3 每月

- Qualified Page Views 与 7-Day Returning Reader Rate。
- 内容域价值事件分布。
- 来源点击与知识图谱导航。
- 排名方法是否产生系统性偏差。
- 英文与中文覆盖差距。
- 来源条款与高风险许可复核。
- 开放数据发行和下游反馈。

## 22. 质量抽检

每周从已发布记录中分层抽样：

- 高影响 Event。
- 普通 Event。
- 模型评测与价格。
- 论文导读。
- GitHub License。
- Prompt 和 Skill 授权。
- 中英文翻译。
- 关系与 Backlink。
- Ask 答案。

每条使用同一检查维度：事实、来源、时间、版本、权利、本地化、关系和页面表现。

质量问题记录到可操作类别，避免只写“内容不好”。

## 23. 事故处理

### 23.1 事故类型

- 核心来源长时间停止更新。
- 批量错误聚类或实体合并。
- 受限内容进入公开页面或数据包。
- 私人信息或密钥泄漏。
- 排名计算错误。
- Ask 批量无引用或错误引用。
- 错误 Daily Brief 已通过邮件发送。

### 23.2 响应顺序

1. 限制继续传播：暂停发布、索引、邮件或 Release。
2. 保留证据：运行 ID、版本、受影响记录和时间。
3. 修正源数据或规则。
4. 重建受影响出口。
5. 发布 Correction、Tombstone 或状态说明。
6. 记录根因和最小预防措施。

不要通过静默清空数据或吞掉错误恢复表面正常。

## 24. 运营仪表盘

Owner 首页只显示可行动信息：

- 核心来源过期数。
- 最近失败任务及原因。
- P0/P1 待核验数。
- 待合并/拆分候选。
- 高影响待审本地化。
- 今日 Brief 状态。
- 待处理更正、下架和投稿。
- Search 与 Ask 异常。
- 下一 Release 状态。

总抓取量、总 token 或总记录数可作为诊断信息，但不占据运营首页核心位置。

## 25. Public Alpha 发布日清单

- 首页与八域无占位入口。
- 当日 Brief 中英文已审。
- 核心来源新鲜度正常。
- Top Stories 有理由且无商业混淆。
- 关键模型价格和榜单截止时间可见。
- Search 中英文抽样通过。
- Ask 引用与拒答抽样通过。
- RSS 可读取，邮件订阅与退订已验证。
- Trust Center 和 Public Alpha 限制可见。
- 更正与下架入口可用。
- Public API 文档和数据版本一致。
- Open Data 演练包通过 rights、privacy、schema 和 checksum 校验。
- 备份与恢复路径已验证。

## 26. 运营成功标准

- Owner 可以在一个后台完成发现、去重、核验、本地化、发布和更正。
- 自动化失败不会被误认为“今天没有新闻”。
- 高影响 Event 可以及时双语发布，同时保留来源和限制。
- Daily Brief 由真实已发布 Event 构成，不是标题拼贴。
- 八域都有可持续的不同维护深度，不要求同样自动化。
- Prompt、Skill 和第三方内容的授权边界在发布前可见。
- 模型比较不会混用版本、评测或价格单位。
- 更正能够传播到所有公开出口。
- AI 的角色是草拟、归类和检查，最终责任与公开判断仍可定位到 Owner。
